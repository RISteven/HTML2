1

¿Qué es Git y qué es GitHub?

Cuando se trabaja en un proyecto de programación —solo o en grupo— tarde o temprano aparece la misma pregunta: "¿cuál es la versión buena del código?". Carpetas llamadas proyecto_final, proyecto_final2 o proyecto_final_v3_AHORA_SI son la señal de que hace falta una herramienta de control de versiones. Para eso existe Git.

Git es un programa que se instala en la computadora y guarda el historial completo de los cambios de un proyecto: quién cambió qué, cuándo y por qué. GitHub es un sitio web que aloja esos proyectos en la nube, permite compartirlos con otras personas y sirve como copia de respaldo centralizada. Git es la herramienta; GitHub es el lugar donde el trabajo hecho con Git se guarda y se comparte.

ConceptoExplicación sencillaAnalogía
GitPrograma instalado en la PC que registra el historial de cambios de un proyecto.El motor: hace el trabajo de guardar versiones
GitHubPlataforma web que aloja los proyectos (repositorios) en internet.El garaje/concesionario: donde se muestra y comparte el auto
Repositorio (repo)La carpeta del proyecto, ya controlada por Git, con todo su historial.Una carpeta con "memoria"
CommitUna "foto" guardada del proyecto en un momento dado, con un mensaje explicativo.Un punto de guardado en un videojuego
CloneDescargar una copia completa de un repositorio remoto a la PC.Sacar una fotocopia del expediente completo
Remote (origin)La dirección del repositorio en GitHub asociada a la copia local.La dirección postal donde se envían los cambios
PushSubir los commits guardados localmente hacia GitHub.Enviar la carta al destinatario
PullBajar a la PC los cambios que otros subieron a GitHub.Recibir la correspondencia nueva
Branch (rama)Una línea de trabajo independiente dentro del mismo proyecto.Un borrador aparte que no afecta la versión final hasta fusionarlo
No hace falta memorizar todo de una vez. Con clonar, agregar, confirmar, subir y actualizar (secciones 6 a 9) ya se puede trabajar en el 90% de los casos de este curso.
2

Requisitos previos

  • Windows 10 u 11 (esta guía usa PowerShell, pero los comandos son los mismos en Git Bash, Linux o Mac).
  • Conexión a Internet para instalar Git y comunicarse con GitHub.
  • Una cuenta gratuita en GitHub (se crea en github.com).
  • Un editor de código: se recomienda Visual Studio Code, que integra Git en su interfaz.
  • Permisos de administrador para ejecutar el instalador de Git.
Anotar el usuario y la contraseña de GitHub en un lugar seguro. GitHub ya no acepta la contraseña para subir código desde la terminal: para eso se usa un Personal Access Token o el inicio de sesión del Git Credential Manager, que se explica en la sección 5.
3

Instalación de Git en Windows

3.1 Verificar si Git ya está instalado

Antes de descargar nada, conviene revisar si el equipo del laboratorio ya tiene Git instalado:

PowerShell — Verificar instalación existente
# Verificar versión de Git
git --version

Si devuelve algo como git version 2.44.0.windows.1, Git ya está instalado y se puede pasar directo a la sección 4.

3.2 Descargar el instalador

Sitio oficial: git-scm.com → botón "Download for Windows". El sitio detecta automáticamente si la PC es de 64 o 32 bits y descarga el instalador correcto (Git-#.##.#-64-bit.exe).

3.3 Pasos del instalador

  1. Ejecutar el archivo .exe descargado y aceptar los permisos de administrador.
  2. Aceptar la licencia (GNU GPL) y hacer clic en Next.
  3. Mantener la carpeta de instalación predeterminada.
  4. En "Select Components", dejar las opciones marcadas por defecto. No es necesario cambiar nada.
  5. En "Choosing the default editor", se puede dejar Vim o cambiar a "Use Visual Studio Code as Git's default editor" si ya está instalado. Esta segunda opción es más cómoda para principiantes.
  6. En "Adjusting the name of the initial branch", elegir "Override the default branch name" → main, que es el estándar actual de GitHub.
  7. En "Adjusting your PATH environment", dejar la opción recomendada: "Git from the command line and also from 3rd-party software". Esto permite usar git desde PowerShell.
  8. En el resto de las pantallas (HTTPS, saltos de línea, terminal, etc.) se pueden dejar todas las opciones por defecto sin problema.
  9. Hacer clic en Install y esperar a que finalice. Luego Finish.
  10. Cerrar y volver a abrir PowerShell para que reconozca el comando git.
Si PowerShell ya estaba abierto durante la instalación, debe cerrarse y abrirse de nuevo. Las ventanas abiertas no detectan los cambios en el PATH.

3.4 Confirmar la instalación

PowerShell — Confirmar Git instalado
# Debe mostrar un número de versión
git --version

# Muestra la ruta del ejecutable
where.exe git
git version 2.44.0.windows.1
4

Configuración inicial de Git

Antes del primer commit, Git necesita saber quién sos. Este nombre y correo quedan grabados en cada commit que se haga, así que conviene usar los mismos datos que la cuenta de GitHub.

PowerShell — Configuración global (una sola vez por PC)
# Nombre que aparecerá en los commits
git config --global user.name "Nombre Apellido"

# Correo asociado a la cuenta de GitHub
git config --global user.email "correo@ejemplo.com"

# Verificar que quedó configurado
git config --list
Esta configuración se hace una sola vez por computadora. Si se trabaja en varios equipos (casa, laboratorio, notebook), hay que repetirla en cada uno.
En una PC del laboratorio compartida con otros estudiantes, revisar con git config --list que el nombre y correo sean los propios antes de hacer un commit, para que el trabajo quede atribuido correctamente.
5

Crear una cuenta y un repositorio en GitHub

5.1 Crear la cuenta

  1. Ingresar a github.com y hacer clic en Sign up.
  2. Completar correo, contraseña y un nombre de usuario (será parte de la URL del perfil, ej. github.com/tu-usuario).
  3. Verificar el correo con el código que envía GitHub.

5.2 Crear un repositorio nuevo

  1. Hacer clic en el botón "+" arriba a la derecha → New repository.
  2. Escribir un nombre corto y sin espacios (ej. proyecto-web-pr2).
  3. Elegir si el repositorio será Public (cualquiera lo ve) o Private (solo invitados).
  4. Marcar "Add a README file" para que el repositorio no quede vacío.
  5. Hacer clic en Create repository.

5.3 Copiar la URL del repositorio

En la página del repositorio, hacer clic en el botón verde "Code" y copiar la dirección. Hay dos formas de conectarse:

MétodoFormato de la URLCuándo usarlo
HTTPShttps://github.com/usuario/repo.gitMás simple para empezar. Pide usuario y token la primera vez. Recomendado para este curso.
SSHgit@github.com:usuario/repo.gitRequiere generar una llave SSH previamente. Cómodo a largo plazo, más pasos iniciales.
Si al hacer git push Windows pide iniciar sesión, va a abrir una ventana del navegador para autenticarse con la cuenta de GitHub (Git Credential Manager). Después de la primera vez, queda recordado.
6

Bajar un proyecto existente — git clone

Cuando el repositorio ya existe en GitHub (por ejemplo, el profesor lo compartió, o es el repositorio del propio proyecto creado desde otra PC), se descarga completo con clone. Esto trae el código y todo el historial de commits.

PowerShell — Bajar el código por primera vez
# Ubicarse en la carpeta donde se quiere guardar el proyecto
cd C:\Users\usuario\Documents

# Clonar el repositorio (trae una carpeta nueva con el nombre del repo)
git clone https://github.com/usuario/proyecto-web-pr2.git

# Entrar a la carpeta descargada
cd proyecto-web-pr2
proyecto-web-pr2/ # carpeta creada por git clone ├── .git/ # historial de Git (no se toca a mano) ├── js/ # código del servidor Node.js ├── public/ # vistas HTML ├── .gitignore # archivos que Git debe ignorar └── README.md # descripción del proyecto
git clone se ejecuta una sola vez por proyecto y por PC. Para traer cambios nuevos después, no se vuelve a clonar: se usa git pull (sección 9).
No clonar un repositorio dentro de otro repositorio ya existente. Ubicarse primero en una carpeta neutral (ej. Documents) antes de clonar.
7

Ver el estado y comparar cambios — status y diff

Antes de guardar o subir nada, siempre conviene mirar qué cambió. Git ofrece dos comandos clave para esto, y son los que más se usan en el día a día.

7.1 git status — qué archivos cambiaron

PowerShell — Ver el estado del repositorio
git status
On branch main Changes not staged for commit: modified: public/menu.html Untracked files: public/reporte.html

Este resultado dice: se modificó menu.html (Git ya lo conocía) y hay un archivo nuevo reporte.html (Git todavía no lo sigue).

7.2 git diff — qué líneas exactas cambiaron

PowerShell — Comparar línea por línea
# Ver cambios aún no agregados al área de preparación
git diff

# Comparar contra una versión anterior específica
git diff HEAD~1

# Comparar la rama actual contra otra rama
git diff main feature-login

Las líneas que empiezan con - son las que se eliminaron; las que empiezan con + son las que se agregaron. Es la forma más precisa de comparar dos versiones del mismo archivo.

7.3 git log — historial de commits

PowerShell — Ver el historial
# Historial resumido, un commit por línea
git log --oneline

# Historial con gráfico de ramas
git log --oneline --graph --all
En GitHub también se puede comparar visualmente sin usar la terminal: pestaña "Compare" del repositorio, o el botón "Compare & pull request" que aparece al subir una rama nueva.
8

Subir cambios — add, commit y push

Subir código a GitHub siempre sigue el mismo ciclo de tres pasos. Vale la pena aprenderlo de memoria porque se repite decenas de veces durante el proyecto.

  1. Agregar los archivos que se quieren guardar al área de preparación (staging).
  2. Confirmar (commit) esos cambios con un mensaje que explique qué se hizo.
  3. Subir (push) los commits guardados localmente hacia GitHub.
PowerShell — Ciclo completo de subida
# 1. Agregar todos los archivos modificados y nuevos
git add .

# También se puede agregar un archivo puntual
git add public/reporte.html

# 2. Confirmar los cambios con un mensaje descriptivo
git commit -m "Agrega pantalla de reporte de usuarios"

# 3. Subir los commits a GitHub (rama main)
git push origin main
Un buen mensaje de commit explica el "qué" en pocas palabras: "Corrige validación del formulario de alta" es útil; "cambios" o "asd" no lo es. Dentro de un año, ese mensaje es lo único que va a recordar por qué se hizo el cambio.
Si git push devuelve un error de rechazo (rejected), significa que GitHub tiene commits que la PC local no tiene todavía. Hay que hacer git pull primero (sección 9) y luego reintentar el push.
9

Actualizar el repositorio local — fetch y pull

Cuando se trabaja en equipo, otras personas suben cambios a GitHub que la copia local todavía no tiene. Antes de empezar a trabajar cada día, conviene actualizar la carpeta local.

git fetch
  • Descarga los cambios nuevos de GitHub.
  • No los mezcla con los archivos locales todavía.
  • Sirve para "mirar" qué hay de nuevo antes de aplicarlo.
git pull
  • Descarga los cambios nuevos de GitHub.
  • Los combina automáticamente con los archivos locales.
  • Equivale a hacer fetch + merge en un solo paso.
PowerShell — Actualizar antes de trabajar
# Forma recomendada para el día a día del curso
git pull origin main
Regla simple para todo el curso: pull antes de empezar, push al terminar. Actualizar primero evita la mayoría de los conflictos.
10

Trabajar con ramas (branches)

Una rama permite probar o desarrollar algo nuevo sin tocar la versión principal del proyecto (main). Es especialmente útil en equipo: cada integrante trabaja en su propia rama y luego se une todo a main.

PowerShell — Crear, cambiar y fusionar ramas
# Ver en qué rama se está y cuáles existen
git branch

# Crear una rama nueva y moverse a ella en un solo paso
git checkout -b feature-login

# Trabajar normalmente: add, commit, push en esta rama
git add .
git commit -m "Implementa formulario de login"
git push origin feature-login

# Volver a la rama principal
git checkout main

# Traer los cambios de feature-login hacia main
git merge feature-login
ComandoQué hace
git branchLista las ramas del repositorio local.
git checkout -b nombreCrea una rama nueva y se posiciona en ella.
git checkout nombreCambia a una rama ya existente.
git merge nombreFusiona la rama indicada dentro de la rama actual.
git branch -d nombreElimina una rama ya fusionada.
En este curso, con un proyecto individual, alcanza con trabajar directo en main. Las ramas se vuelven imprescindibles cuando dos o más personas tocan el mismo repositorio al mismo tiempo.

Errores frecuentes y cómo resolverlos

Error o síntomaCausa probableSolución
git no se reconoceGit no está instalado o el PATH no se actualizó.Cerrar y reabrir PowerShell. Reinstalar si persiste.
fatal: not a git repositoryEl comando se ejecuta fuera de la carpeta del proyecto clonado.Verificar con cd y entrar a la carpeta correcta antes de usar git.
Updates were rejectedGitHub tiene commits que la copia local no tiene.Ejecutar git pull origin main y luego reintentar git push.
Please tell me who you areFalta configurar user.name y user.email.Ejecutar los comandos de la sección 4 antes de commitear.
CONFLICT (content)Dos personas modificaron las mismas líneas del mismo archivo.Abrir el archivo, resolver manualmente las marcas <<<<<<<, luego git add y git commit.
remote: Support for password authentication was removedGitHub ya no acepta la contraseña de la cuenta para autenticar por HTTPS.Usar el inicio de sesión del navegador (Credential Manager) o crear un Personal Access Token.
nothing to commit, working tree cleanNo hay cambios nuevos desde el último commit.No es un error: significa que todo ya está guardado.

11.1 Resolver un conflicto de fusión

Cuando aparece un conflicto, Git marca el archivo con símbolos especiales que hay que editar a mano:

Archivo con conflicto sin resolver
<<<<<<< HEAD
<h1>Bienvenido al sistema</h1>
=======
<h1>Bienvenido, iniciar sesión</h1>
>>>>>>> feature-login
  1. Decidir qué versión queda (una, la otra, o una combinación de ambas).
  2. Borrar las líneas <<<<<<<, ======= y >>>>>>>.
  3. Guardar el archivo y ejecutar git add archivo.
  4. Completar la fusión con git commit.
12

Checklist final y resumen de comandos

Verificar cada punto antes de considerar dominado el flujo básico de GitHub:

  • Git instalado y verificado con git --version.
  • Nombre y correo configurados con git config --global.
  • Cuenta de GitHub creada y repositorio del proyecto disponible.
  • Proyecto descargado correctamente con git clone.
  • Capaz de revisar cambios con git status y git diff.
  • Ciclo add → commit → push ejecutado sin errores.
  • Repositorio local actualizado con git pull antes de empezar a trabajar.
  • Concepto de rama (branch) comprendido, aunque no se use a diario.
ComandoQué hace
git --versionConfirma que Git está instalado
git config --globalConfigura nombre y correo del autor de los commits
git clone URLBaja un repositorio completo por primera vez
git statusMuestra qué archivos cambiaron
git diffCompara los cambios línea por línea
git log --onelineMuestra el historial de commits
git add .Prepara todos los cambios para el commit
git commit -m "mensaje"Guarda una versión con un mensaje descriptivo
git push origin mainSube los commits locales a GitHub
git pull origin mainBaja y combina los cambios nuevos de GitHub
git branch / checkout -bLista o crea ramas de trabajo
git merge nombreFusiona una rama dentro de la actual
Con estos doce comandos se cubre prácticamente todo el trabajo diario con GitHub en un proyecto académico. El resto de las funciones (Pull Requests, Issues, Actions) se aprenden progresivamente cuando el proyecto lo requiere.
